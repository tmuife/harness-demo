## Context

本 change 配套 `add-harness-architecture-explorer`，当前仅规划。前端第一阶段使用现有 API 和集中的教学展示适配，能够独立运行。用户要求先查看前端效果再决定是否继续，因此文档齐备不等于可以实施本 change；需先记录用户继续决定及其对前端效果的反馈。

当前 `catalog.py` 中的 `_COMPONENTS` 有 11 个 ID/标题，但 `/api/capabilities` 仅返回被 Demo 引用的组件。`TaskBrief` 缺少业务背景，`DemoTask` 缺少直接的任务目标，而且 `_task()` 为所有 Demo 生成相同完成条件。这些是后端配套工作的实际范围。Demo 1–6 的执行代码和现有结构化证据已能支撑第一版界面。

## Goals / Non-Goals

**Goals:**

- 为通过评审的架构首页提供单点维护的组件职责、分组、覆盖状态和任务元数据。
- 修正任务说明与只读分析、受控停止等实际行为不一致的表达。
- 兼容现有调用方，并把扩展数据接入已验收的前端页面。

**Non-Goals:**

- 不重写六个 Demo、PLAIN 基线、runner、SSE、审批协调或确定性评价。
- 不新增子 Agent Demo、任意任务编辑、用户配置的图关系、联网 provider 或执行拓扑追踪。
- 不让服务端负责画布坐标、像素尺寸、动画、选中状态或主题。

## Decisions

### 1. 前端评审决定后端实施时机

开始任务前确认前端已实现并向用户展示，且用户明确要求继续此 change；若条件未满足，仅保留文档。根据实际评审结果核对以下契约，如需求改变先更新 artifacts，而不是机械实现预设字段。只实施第一个 change 的指令不包含对本 change 的授权。

### 2. 新增有界的只读组件目录

采用 `GET /api/harness-components`，返回一个完整的 typed list，每项包含：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `id` | string | 沿用现有 11 个稳定组件 ID |
| `title` | string | 中文名称 |
| `description` | string | 公开、简短的教学职责 |
| `groupId` | enum | `orchestration`、`information`、`execution`、`verification`、`continuity`、`control` |
| `coverage` | enum | `primary`、`supporting`、`not_demonstrated` |

组 ID 与前端第一阶段设计一致；组的显示布局和样式属于前端。coverage 从 capability 关系计算：至少一个主要关系为 primary，否则至少一个支撑关系为 supporting，否则 not_demonstrated。这表示教学覆盖，不代表组件独立可运行或运行成功；能力是否可运行仍只看 capability.status。`subagents` 当前为 not_demonstrated。

保留 capability 内现有 `HarnessComponent{id,title}` 结构，内部组件定义统一供它和新目录使用。新 API 不重复输出 Demo 列表或存储第二份关系；前端继续反向关联 primary/supporting 数组。相较于替换所有旧接口的新聚合协议，该独立只读列表更易兼容，也能表达未被任何 Demo 引用的组件。

目录为固定 11 项，无分页、用户写入接口、LLM 生成内容或运行期工作区扫描。使用现有模块和 Pydantic 明确响应模型，不增加通用目录框架。

### 3. 向现有任务响应添加字段并校正说明

`TaskBrief` 保留 `id/title/summary`，新增 `businessBackground: string | null` 和 `sharedConstraints: string[]`，模型默认分别为 null 和空数组。`DemoTask` 保留所有已有字段，新增 `objective: string | null`，默认 null。生产目录为六个 Demo 填充有效值，默认值用于兼容构造方及过渡；前端仍支持旧响应缺字段。

背景和约束基于公开合成任务，只描述所有实验适用的场景/边界。不公开完整系统提示词、测试源码、凭据或绝对工作区路径。任务目标和完成条件按 Demo 显式声明，减少难以审查的共享生成规则：

- Understand：分析规则及约束、说明输入来源、工作区保持未修改；不要求写代码或通过实现测试。
- Act：区分 PLAIN 建议与 HARNESS 实际操作；代码完成声明需固定验证，不能把仅建议说成已执行。
- Prove：说明有限反馈轮次和停止条件；不要求每次必须先失败后成功。
- Control：分别解释门禁是否生效与任务是否完成；批准/拒绝/超时均可产生真实控制证据，拒绝不能写成任务成功。
- Continue：说明会话隔离、交接有效性和 Session B 的任务结果；不宣称长期记忆或保证成功恢复。
- Ground：说明本地模拟当前政策的来源与版本，以及实际取用和契约验证；不宣称联网或保证获取成功。

修改这些字段只改变公开教学契约，不参与 runner 分派、工具授权或结果评价。若核对发现实际执行缺陷，记录并另行确定修复范围，不能用文案掩盖。

### 4. 必要的前端接线包含在本 change 内

在第一阶段的 API/类型/展示适配模块中增加新字段和可选组件目录请求。核心 `/api/capabilities` 与 `/api/task` 加载规则保持不变；新组件目录独立处理，不加入会阻塞核心目录的全有或全无 Promise。

- 新目录有效时使用服务端职责、组 ID 和覆盖信息；布局仍取本地已验收规则。
- 新任务字段有效时优先使用；缺失时保留第一阶段摘要回退。
- 新目录 404、网络错误或形状非法时，沿用第一阶段完整教学目录并给出简短非阻塞提示，不屏蔽有效能力或当前实验。
- 对新目录校验完整已知 ID、唯一 ID、非空说明、组 ID 和 coverage 枚举；不渲染不受控 HTML。遇到不兼容内容按整个可选目录回退，避免混合出不一致关系。
- 核心目录失败仍禁止开始实验；可选目录成功不能替代 capability.status 授权。

接线只改变来源，不重新排版或加入新交互。保留最小旧服务回退数据，当前有效服务器数据为首选事实源。

### 5. 一致性检查基于静态目录与确定性测试

验证所有 capability 组件引用存在且名称一致、同一 capability 的 primary/supporting 不重叠、组件 ID 唯一、覆盖状态推导正确、六项 objective 非空、Demo 编号与分派一致。测试旧请求响应字段、枚举和禁止任意 capability 配置的边界；元数据 GET 不读取凭据、不创建工作区、不启动实验。

用 fake client 保留六 Demo 与 API 回归。前端测试新目录接入、旧响应回退、可选目录失败不阻塞、任务预览与详情一致性，不为本次元数据调整增加真实网络测试。

## Risks / Trade-offs

- [前端评审后需求变化] → 实施前核对并更新契约；当前设计是待用户决定实施的具体方案。
- [元数据改善被误解为实验能力增加] → API 和 UI 明确教学覆盖，保留未覆盖节点和真实结果语义。
- [新接口短暂不可用导致首页不可用] → 可选请求独立加载，旧数据回退，核心运行接口保持原样。
- [分组或任务文案在两侧漂移] → 服务端优先，集中适配，确定性映射与前端接线测试。
- [借机扩大后端重构范围] → 限于 catalogue、公开模型、只读端点及测试，执行缺陷另行评估。

## Migration Plan

1. 核对前端交付和用户继续决定，更新因评审而变化的字段/文案。
2. 先增补后端公开模型和单点目录，再添加只读端点，运行确定性检查。
3. 接入第一阶段前端适配，验证新/旧服务兼容和回退，不移除现有端点。
4. 运行后端 pytest/Ruff、前端 lint/test/build，检查六项任务预览和完整详情、子 Agent 状态、核心实验创建与审批回归。
5. 更新受影响的 API/前端 README。若需回滚，新前端可回退到旧后端数据，旧前端可忽略新字段；无需数据迁移。

## Open Questions

- 用户查看前端效果后是否继续、是否调整分组和文案？本 change 必须等待此决定。
- 精确组件执行状态不在当前契约内；如果评审需要该能力，需重新确定真实事件、证据和界面范围。
