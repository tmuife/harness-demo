## Context

当前 Web runner 使用 `redirect_stdout` 捕获已有 CLI 输出，并按换行符创建 `ExperimentEvent`。只有带方括号前缀的行能够切换 stage，其余模型正文、Diff 和 pytest 输出继承上一 stage，因此一个操作会被拆成大量标题相同的事件。前端随后直接渲染全部事件，并用通用 JSON 展示少量 evidence。虽然数据是有界和安全的，但页面要求用户先解释实现日志，才能理解实验结论。

现有设计和主规格已经要求摘要与证据分层、最终结果来自确定性评价；本变更补齐事件生产、结果快照和页面呈现之间缺少的语义结构。改动横跨 Python Web 适配层、SSE/结果模型和 React 实验界面，同时必须保持 CLI 行为、真实 LLM 调用、顺序运行、断线恢复和工作区安全边界。

## Goals / Non-Goals

**Goals:**

- 让非实现者先理解本次运行结论、能力差异和客观依据。
- 让一次有意义的操作对应一个事件，把多行内容保留为可展开证据。
- 为 Understand、Act、Prove 提供符合各自目标的确定性指标和结论模板。
- 在运行态提供简洁进度，在完成态提供按阶段对齐的两侧比较。
- 保留可供工程排错的完整结构化记录，并继续执行脱敏、截断和安全文本渲染。

**Non-Goals:**

- 不改变 Demo 任务、提示词、模型配置、工具权限、评价规则或 PLAIN/HARNESS 顺序。
- 不把单次实验升级为统计 benchmark，不计算跨实验胜率或持久化历史。
- 不实现仍处于 planned 状态的 Control、Continue 或 Ground Demo。
- 不要求 Web 页面逐字复现 CLI stdout，也不改变 CLI 面向终端的标签格式。
- 不引入新的前端状态库、日志服务或数据库。

## Decisions

### 1. 使用显式的类型化报告边界代替按行推断 stage

共享 Demo 流程将在已有关键操作边界发出类型化展示事件。一个轻量 reporter 接口负责接收 input、LLM、tool、write、test、feedback 和 result 数据；CLI sink 将其渲染为现有终端文本，Web sink 将其保存为 API 事件。需要展示的模型正文、Diff 和测试输出作为事件 evidence 一次传入。

选择显式报告而不是继续改进前缀解析，是因为无前缀正文无法可靠区分模型文本、代码和日志边界。仅在前端合并相邻事件同样依赖当前偶然的输出顺序，无法稳定生成测试次数、反馈次数等指标。报告边界保持小而具体，不建立通用遥测框架。

迁移期间可以保留受控的 stdout 捕获用于 CLI 兼容检查，但 stdout 不再是 Web 语义事件的事实来源。每个操作只发出一个公开事件，事件仍沿用稳定 ID、单调 sequence、side、stage、status 和 occurredAt 字段。

### 2. 事件摘要与 stage 专属证据分离

所有事件继续提供适合讲解的 `title` 和 `summary`。evidence 将按 stage 使用受控字段：

- input：来源文件标签和上下文数量，不返回未受限提示词；
- llm：轮次、输出摘要和经过截断的模型输出；
- tool：工具名、受控参数摘要、成功或拒绝状态和有界结果；
- write：允许的相对路径、字符数和有界 Diff；
- test：固定命令标签、退出码、通过/失败数量、失败项和有界输出；
- feedback：目标轮次、失败摘要和是否已返回模型；
- result：调用、修改、测试、规则检查和终态事实。

后端使用明确的 Pydantic evidence 模型或集中式构造函数验证字段；前端使用与 stage 对应的 TypeScript 判别联合渲染。API 不接受任意 HTML，未知字段不进入默认证据 UI。通用 JSON 只在完整记录视图中作为安全文本提供。

选择 stage 专属证据而不是保留 `Record<string, unknown>` 的自由渲染，是为了让字段能被测试、翻译和无障碍标记，同时避免把内部对象意外暴露到页面。

### 3. 最终快照承载客观事实，确定性模板生成讲解结论

每侧 RunSnapshot 将提供形成展示所需的结构化事实，例如输入来源、调用次数、修改文件、测试次数、反馈次数、最终测试状态和 Demo 1 分析检查。实验完成后，根据 capability ID 和两侧事实生成 `comparison` 数据，包括限定为“本次运行”的观察摘要和有序指标行。

结论模板必须是确定性的，不调用额外 LLM，也不从模型自述推断成功。模板只描述已记录事实：

- Understand：比较上下文来源、规则识别和未修改状态；
- Act：比较仅建议、实际写入、固定测试和范围检查；
- Prove：比较生成、测试、反馈次数及最终测试。

后端负责结果事实和能力指标的统一含义，前端负责布局与可访问表达。这样刷新恢复得到的页面与流式运行结束时一致，也避免多个客户端各自重新解释原始文本。

### 4. 使用“结论—指标—阶段—证据”渐进展示

运行过程中保留两侧简洁状态，但每次仅追加语义步骤。两侧结束后，完成视图在长内容之前展示：

1. 本次运行观察和非 benchmark 提示；
2. PLAIN/HARNESS 终态与能力定制指标；
3. 获得信息、采取行动、执行验证、接收反馈、形成结论的阶段对照；
4. 可展开的类型化证据；
5. 完整结构化记录入口。

桌面端阶段表按列对齐两侧；移动端每个阶段卡片依次包含 PLAIN 和 HARNESS 两行，避免在两个标签页之间记忆和对照。阶段采用“核心阶段 + 能力焦点阶段 + 实际事件阶段”的确定性可见规则：

- `获得信息` 和 `形成结论` 是讲解起点与终点，始终显示；
- Understand 不额外强制阶段，Act 强制显示 `采取行动` 和 `执行验证`，Prove 强制显示 `采取行动`、`执行验证` 和 `接收反馈`；
- 除上述阶段外，只要任一侧产生了对应语义事件，该阶段也显示；
- 两侧均无事件且不属于所选能力焦点的阶段默认省略，避免用空行稀释能力差异。

可见阶段中某一侧没有事件时必须显示中性且基于事实的缺失说明，例如“未提供该能力”“本次未执行”或“暂无证据”。只有结构化结果证明首轮验证通过时，才可显示“无需反馈（首轮验证通过）”；不得把没有事件自行解释为成功、失败或模型选择。

选择阶段对齐而不是两条完成后仍独立滚动的时间线，是因为 Harness 的作用通常表现为某阶段是否存在，例如 Act 的真实写入或 Prove 的反馈循环。原始 chronology 仍可在完整记录中查看。

### 5. 完整记录是排错视图，不是默认叙事

完整记录首版采用当前页面讲解内容之后的独立区域，不使用侧边抽屉、模态框或独立路由。该区域默认收起，由“查看完整记录”操作展开；展开后按全局 sequence 显示所有结构化事件，并使用明确的 PLAIN/HARNESS 标签以及“全部 / PLAIN / HARNESS”筛选。这样长 Diff 和日志可以使用页面内容宽度，移动端也能沿正常文档流阅读，而不会遮挡结论或引入复杂的焦点陷阱。

展开操作使用 `aria-expanded` 和 `aria-controls` 关联独立区域。区域标题可获得程序化焦点，收起后焦点返回触发控件；筛选不得改变事件本身或两侧终态。完整记录展示所有结构化事件、时间、sequence、status 和可公开 evidence。它不是宿主 stdout 的逐字镜像；其完整含义是 API 已记录的全部语义操作和受限证据。长文本继续使用现有上限、内部滚动和复制操作，模型输出、日志与 Diff 均以纯文本安全渲染。

选择同页独立区域而不是抽屉，是因为完整记录包含宽 Diff、日志和两侧标签，抽屉会在桌面端压缩证据，在移动端退化为全屏覆盖，并增加关闭与焦点管理成本。同页区域既保留讲解上下文，也能被浏览器搜索和辅助技术按正常阅读顺序访问。这样既保留工程人员定位问题的能力，也避免为了“完整”重新引入逐行事件。SSE 无需增加第二条原始日志通道。

### 6. 保持传输、恢复和安全兼容

SSE 的事件 ID、Last-Event-ID、sequence 排序、终态关闭和结果快照校准保持不变。事件 payload 可以增加结构化字段，但现有顶层字段不删除；前后端作为同仓版本同步升级。所有路径必须为工作区相对路径，输出继续在后端脱敏和截断，错误不得包含 SDK 请求、认证头、API Key 或宿主机绝对路径。

CLI 与 Web 使用同一组操作事实，但可以有不同渲染：CLI 保留紧凑标签，Web 使用讲解摘要和 evidence。确定性测试使用假 Responses client，不访问网络。

## Risks / Trade-offs

- [显式事件可能与 CLI 文本发生差异] → 让操作事实先进入 reporter，再由 CLI/Web sink 分别渲染，并用现有 CLI 测试保护终端标签和结果。
- [类型化 evidence 增加前后端模型数量] → 只覆盖现有三个 Demo 的实际字段，按 stage 复用小模型，不建立通用遥测模式。
- [能力定制模板可能掩盖异常组合] → 模板只陈述结构化事实，未知或缺失事实显示“无可用证据”，完整记录始终可查看。
- [完成态切换布局造成视觉跳动] → 运行时预留结果区域，终态只收束现有步骤并遵守 `prefers-reduced-motion`。
- [旧实验快照与新前端类型不兼容] → 后端当前只保留 30 分钟内存状态；部署时允许旧记录自然失效，前端对缺失新字段提供中性回退。
- [语义事件仍可能很多] → 多轮操作按阶段分组，默认折叠重复轮次；不得通过丢弃事件来制造简洁视图。

## Migration Plan

1. 扩展后端事件和结果模型，先增加兼容字段及其安全构造测试。
2. 为 Demo 1–3 引入类型化报告边界和 sinks，验证 CLI 输出、结果评价与原行为一致。
3. 更新 Web runner，停止将 stdout 行发布为默认事件，并验证 SSE 排序、重放和终态快照。
4. 更新前端类型、reducer 和证据渲染，再加入能力摘要与阶段对照布局。
5. 运行后端 pytest/Ruff 和前端 lint/test/build，并分别用 Understand、Act、Prove 的固定假客户端快照验证讲解结果。

回滚时前后端作为一个版本回滚到旧事件适配；不涉及数据库或持久数据迁移。短期内存实验可在服务重启后清除，页面按既有恢复失败流程返回初始状态。
