## Context

当前项目是一个 Python Harness 对照演示，通过 `harness-demo <编号> [--harness]` 使用真实 LLM 运行同一运费规则任务。Demo 1 至 Demo 3 已实现，分别隔离展示项目上下文、受限工具行动和测试反馈循环；Demo 4 至 Demo 6（边界与审批、跨会话状态、外部依据）目前只有设计。

仓库已按两个独立服务组织：

```text
demonstration/
├── frontend/   # React + TypeScript + Vite
└── backend/    # Python 3.12 + uv Harness 演示
```

本变更设计一个面向演示观众的“Harness Lab / 能力对照实验台”。界面需要让用户选择 Harness 能力，并理解相同任务在 PLAIN 与当前 Harness 配置下获得的输入、采取的行动和产生的客观工程结果。前端不能直接持有 LLM 凭据、访问演示工作区或执行命令，所有真实运行能力必须位于 Python 后端。

## Goals / Non-Goals

**Goals:**

- 用一个主页面完成能力选择、任务展示、实验运行、过程观察和结果对比。
- 清晰呈现六类 Harness 能力，同时准确区分“可真实运行”和“设计中”。
- 并排展示 PLAIN 与 Harness 两条运行轨道，使实验变量和结果差异无需切换页面即可理解。
- 以结构化事件实时展示输入、LLM、工具、写入、测试、反馈、审批、交接、依据和最终结果。
- 将 Diff、测试输出、调用次数、文件范围和来源版本等证据作为一等信息，而不只展示模型回答。
- 保持前端结构简单、类型明确、可响应式使用，并为后续扩展六项能力的真实运行预留稳定接口。
- 保留现有 CLI；Web UI 与 CLI 最终复用同一套后端 Demo 逻辑和安全边界。

**Non-Goals:**

- 本变更不调整已经完成的 `backend/` 目录迁移，也不改变现有 CLI 行为。
- 本阶段不实现 Demo 4 至 Demo 6 的 Python 运行逻辑。
- 本阶段不支持任意多能力组合的真实编排，也不宣称组合结果构成公平 benchmark。
- 不在浏览器中保存或传递 API Key，不提供任意文件读写、任意 shell 或自定义工作区路径。
- 不引入通用 Agent 框架、工作流设计器、用户系统、数据库或历史运行管理平台。
- 不为未实现能力生成看似真实的模拟结果。

## Decisions

### 1. 使用 React、TypeScript 和 Vite 作为独立前端服务

前端位于 `frontend/`，使用函数组件、Hooks 和严格 TypeScript。Vite 提供轻量的开发与构建流程，适合当前单页面演示，不引入 Next.js 的服务端渲染、路由和部署复杂度。

第一阶段不引入组件库、全局状态库或请求状态库。实验只在单页内运行，本地 reducer 足以表达 `idle → starting → running → completed/failed` 状态；当真实复用出现后再抽取共享组件。

建议结构：

```text
frontend/src/
├── features/
│   └── experiment/
│       ├── components/
│       │   ├── CapabilityPanel.tsx
│       │   ├── TaskBrief.tsx
│       │   ├── ComparisonLanes.tsx
│       │   ├── EventTimeline.tsx
│       │   ├── EvidenceDrawer.tsx
│       │   └── ResultSummary.tsx
│       ├── api/
│       │   └── experimentApi.ts
│       ├── experimentReducer.ts
│       ├── types.ts
│       ├── styles.css
│       └── index.tsx
├── shared/
│   └── components/
├── App.tsx
└── main.tsx
```

### 2. 主界面采用“实验控制台”而不是聊天应用布局

桌面端使用左侧能力控制区和右侧对照工作区。任务工单保持在顶部可见，右侧主体是 PLAIN 与 HARNESS 两条等宽轨道。每条轨道内部按时间展示事件，结束后在同一位置显示结果摘要。

```text
┌──────────────────────── Harness Lab ────────────────────────┐
│ 同一任务 · 同一模型 · 干净工作区                 Run status │
├──────────────────┬──────────────────────────────────────────┤
│ 六项能力选择      │ 当前任务                                 │
│                  ├────────────────────┬─────────────────────┤
│ □ Understand     │ PLAIN              │ HARNESS             │
│ □ Act            │ event timeline     │ event timeline      │
│ □ Prove          │                    │                     │
│ □ Control        ├────────────────────┴─────────────────────┤
│ □ Continue       │ Evidence / Diff / Tests / Result          │
│ □ Ground         │                                           │
│ [开始对照]        │                                           │
└──────────────────┴───────────────────────────────────────────┘
```

移动端将能力面板折叠到顶部，PLAIN 与 HARNESS 使用两个保持可见状态的标签页；结果摘要仍同时列出两侧关键指标，避免移动端横向压缩日志和 Diff。

视觉采用工程实验台风格：石墨色背景、暖白文本、酸橙色表示启用能力、橙色表示等待/审批、红色表示失败。正文与标题使用具有编辑感的字体组合，事件、代码和测试证据使用等宽字体。动效集中在运行开始时的轨道激活、事件进入和最终结果收束，并遵守 `prefers-reduced-motion`。

### 3. 六项能力由声明式元数据驱动，但第一阶段只允许单选真实实验

界面将六个能力显示为可勾选控制项，每项包含名称、解释、证据类型和可用状态：

| ID | 名称 | 当前状态 | 核心证据 |
| --- | --- | --- | --- |
| `understand` | 项目上下文 | 可运行 | 输入文件、规则识别项 |
| `act` | 受限工具行动 | 可运行 | 工具调用、文件 Diff、测试 |
| `prove` | 测试反馈循环 | 可运行 | 各轮测试、反馈、调用次数 |
| `control` | 边界与审批 | 设计中 | 审批、拒绝、作用域检查 |
| `continue` | 跨会话状态 | 设计中 | 会话交接、重复工作、下一步 |
| `ground` | 外部依据 | 设计中 | 工具来源、政策版本、生效日期 |

虽然视觉上使用 checkbox 表达能力的启用/关闭，第一阶段 reducer 对可运行配置实施最多一项的约束。选择另一项会替换当前选择；设计中能力可展开查看说明，但不会启用运行按钮。界面明确解释该限制来自当前后端的“单 Demo、单实验变量”模型。

后续后端具备组合编排能力时，前端可只调整配置校验规则，将请求中的 `capabilities` 从单元素数组扩展为多元素数组，无需重构展示层。组合能力始终配置在 HARNESS 侧，PLAIN 侧保持固定基线；本产品不提供任意“配置 A vs 配置 B”模式。

### 4. PLAIN 是固定基线，两侧按顺序执行

每次点击“开始对照”都由后端为两侧创建独立、干净且输入任务相同的工作区。PLAIN 侧只获得该实验定义的基线能力；HARNESS 侧只增加当前选择的目标能力。运行期间锁定配置，防止界面显示的能力与已提交实验不一致。用户可取消当前展示或等待结束后重置并运行新配置。

后端先完整执行 PLAIN，再开始 HARNESS。前端可同时展示两条轨道，但 HARNESS 轨道在基线完成前显示“等待基线完成”。顺序执行能够保持“先观察问题，再观察 Harness 改善”的讲解节奏，并避免两次真实 LLM 调用同时触发供应商并发限制。第一阶段不提供并行开关。

两侧都必须显示模型、任务、运行状态和开始时间。差异摘要不直接将“模型回答更长”视为成功，而优先比较以下工程证据：

- 获得的输入来源；
- 实际工具与文件操作；
- 测试是否执行、是否反馈以及最终状态；
- 是否保持允许的文件范围和公共 API；
- LLM 调用轮次及 Harness 特有事件。

### 5. 后端通过结构化 REST + SSE 接口提供运行数据

浏览器不执行现有 CLI，也不解析控制台文本。`backend/` 应将现有 Demo 输出逐步收敛为结构化事件，同时继续打印适合 CLI 的文本。

建议接口：

```text
GET  /api/capabilities
GET  /api/task
POST /api/experiments
GET  /api/experiments/{experiment_id}/events   # text/event-stream
GET  /api/experiments/{experiment_id}/result
POST /api/experiments/{experiment_id}/cancel   # 可选，只有后端可安全停止时实现
```

创建请求：

```json
{
  "taskId": "shipping-policy-upgrade",
  "capabilities": ["understand"]
}
```

创建响应返回 `experimentId`、两侧运行 ID 和服务端确认后的能力配置。事件统一包含：

```json
{
  "id": "evt_12",
  "experimentId": "exp_24",
  "side": "harness",
  "stage": "test",
  "status": "passed",
  "sequence": 12,
  "occurredAt": "2026-09-07T10:00:00Z",
  "title": "验证通过",
  "summary": "6 passed",
  "evidence": {
    "returncode": 0,
    "output": "......"
  }
}
```

`stage` 使用受控联合类型：`input | llm | tool | write | test | feedback | approval | handoff | grounding | result | error`。前端按 `id` 去重、按 `sequence` 排序；SSE 断线后使用 Last-Event-ID 重连，完成事件后再请求最终结果快照，以恢复可能遗漏的末尾事件。

选择 SSE 而不是 WebSocket，是因为运行过程主要是服务端到浏览器的单向事件流。审批功能未来可通过独立 REST 动作提交，不需要为首版维护双向长连接。

后端使用内存保存运行状态、事件和最终结果，并为已结束实验设置 30 分钟 TTL。前端在 `sessionStorage` 中保存最近一次 `experimentId`；页面刷新后使用结果接口恢复仍在 TTL 内的实验。服务重启或 TTL 到期导致结果不可恢复属于第一阶段的可接受限制，不为此引入数据库。

### 6. 对话、事件和证据分层展示

时间线默认只展示适合讲解的摘要，不直接倾倒完整提示词和测试日志。事件展开后显示经过后端脱敏、截断的证据：

- LLM 事件显示模型可见输入的来源标签和受限输出；
- Tool 事件显示工具名、受控参数摘要和执行结果；
- Write 事件显示允许路径与 Diff；
- Test/Feedback 事件显示测试摘要和是否反馈给模型；
- Approval/Handoff/Grounding 事件使用各自的结构化字段；
- Result 事件显示 PASS/FAIL、约束检查和调用次数。

Evidence Drawer 只消费后端明确标记为可展示的字段，不接受任意 HTML。代码和日志使用纯文本渲染；如果后续增加语法高亮，也必须先转义内容。

Demo 4 的待审批事件直接在 HARNESS 时间线中渲染为内联审批卡片。卡片显示计划动作、目标范围和“批准/拒绝”操作；提交后立即固化为只读审批记录，再由后续事件继续时间线。审批不使用阻塞式弹窗，以免割裂操作请求与审批结果的上下文。

### 7. 明确定义加载、空、错误和不可用状态

- 初始加载：能力与任务使用骨架状态，运行按钮禁用。
- 无选择：展示如何开始以及六项能力的差异，不创建实验。
- 设计中：展示能力说明、预期证据和后端缺失原因，不出现模拟 PASS/FAIL。
- 启动失败：保留已选配置并显示可重试错误。
- 流中断：显示“正在重连”，已有事件不清空；超过上限后允许查询结果快照。
- 页面刷新：读取 `sessionStorage` 中最近一次实验 ID，并向后端恢复仍在保留期内的事件和结果；不存在或已过期时回到初始状态。
- 单侧失败：另一侧继续展示，结果摘要标记实验不完整，不将基础设施错误当作模型失败。
- 长文本：时间线摘要限制行数，详情抽屉内部滚动并提供复制操作。
- 运行中：锁定能力选择和开始按钮，防止重复提交。

### 8. 安全边界继续由后端强制执行

前端只提交受控 task ID 和 capability ID。工作区路径、模型配置、API Key、工具定义、允许写入路径和测试命令都由后端根据服务端注册表决定。错误响应不得包含认证头、原始 SDK 请求、宿主机绝对路径或未截断的子进程输出。

前端开发服务器通过环境变量配置公开的 API base URL，但任何以 `VITE_` 开头的变量都不得包含秘密。生产环境优先让前后端位于同一站点或由反向代理提供 `/api`，减少 CORS 配置和凭据暴露面。

## Risks / Trade-offs

- [六个 checkbox 暗示可任意组合，但后端当前只能运行单能力实验] → 第一阶段在控件旁明确显示“单变量对照”，由配置校验强制最多选择一个可运行能力，并将组合运行列为后续能力。
- [Demo 4 至 Demo 6 只有设计，完整六项界面可能让观众误以为均已实现] → 使用一致但显著的“设计中”状态，禁用真实运行并展示预计证据，不提供伪造时间线。
- [顺序运行 PLAIN 与 HARNESS 会延长等待时间] → 两条轨道持续显示明确状态和已完成证据；优先保证现场叙事清晰与供应商调用稳定，确认等待成为实际问题后再评估并行模式。
- [将现有 `print()` 流程改成事件可能导致 CLI 与 Web 行为分叉] → 后端使用同一事件对象驱动控制台渲染和 SSE 发布，Demo 逻辑不维护两套状态机。
- [SSE 中断可能造成重复或遗漏事件] → 事件使用稳定 ID 与单调 sequence，前端去重排序，运行结束以结果快照校准。
- [测试输出、模型文本或 Diff 过长会拖慢页面] → 后端保持现有截断策略，前端摘要懒展开并限制 DOM 中同时渲染的内容。
- [前后端目录独立后，开发命令和相对路径容易混用] → 根 README 明确工作目录；前端只依赖 `/api` 契约，不引用 Python 源文件路径。
- [内存结果在服务重启或 TTL 到期后丢失] → 第一阶段明确不承诺历史记录；前端恢复失败时回到初始状态，需要持久历史后再引入存储。

## Migration Plan

1. 在 `frontend/` 独立完成静态界面与类型模型。
2. 在 `backend/` 增加只读能力/任务接口及实验事件模型，使 CLI 输出能够由结构化事件生成。
3. 依次接入已实现的 Demo 1、Demo 2、Demo 3，并验证 PLAIN/HARNESS 工作区隔离和结果一致性。
4. 前端接入创建实验、SSE 事件和最终结果接口，完成加载、失败、重连和响应式验证。
5. Demo 4 至 Demo 6 后端实现后逐项将能力状态从 `planned` 切换为 `available`。

回滚时可以停止部署前端或移除 `/api` Web 入口，现有 CLI 仍应独立可用；前端构建产物不参与 Python Demo 的执行路径。
