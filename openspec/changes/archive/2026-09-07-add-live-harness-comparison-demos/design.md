## Context

本变更最初在 Python 3.12 `uv` 项目中实现真实 LLM、编号化 Demo 和 `--harness` 成对对照。实现现已位于 `backend/`；Demo 1 至 Demo 3 可运行，本文保留其设计决策以及 Demo 4 至 Demo 6 的后续方向。除特别说明外，后端内部路径均相对于 `backend/`。

本变更使用一个统一的“运费规则升级”任务贯穿全部 Demo。这样观众只需理解一次业务背景，就可以把注意力放在每次新增的 harness 能力上。演示面向现场讲解，优先要求短小、可读和结果直观，不要求形成可扩展的智能体框架。

固定工单为：

> 更新运费计算器，使其符合当前配送政策。保持 `calculate_shipping_fee` 公共函数签名不变，不要修改测试来使测试通过，完成后运行项目规定的验证命令。

公共 API 为：

```python
def calculate_shipping_fee(
    subtotal_cents: int,
    destination: str,
    is_member: bool = False,
) -> int:
    ...
```

当前合成政策为：

| 场景 | 预期结果 |
| --- | --- |
| 国内普通用户，订单不足 5000 分 | 运费 800 分 |
| 国内普通用户，订单达到或超过 5000 分 | 免运费 |
| 国内会员，订单不足 3000 分 | 运费 800 分 |
| 国内会员，订单达到或超过 3000 分 | 免运费 |
| 国际订单 | 固定运费 2000 分，不参与免运费 |

初始实现故意使用错误的边界比较，并且没有正确处理国际订单。任务代码保持在几十行以内，确保测试失败能被非领域专家快速理解。

## Goals / Non-Goals

**Goals:**

- 每个正常演示命令都通过官方 OpenAI Python SDK 实际调用 LLM。
- 使用 `uv run harness-demo <编号>` 和 `uv run harness-demo <编号> --harness` 形成清晰的成对实验。
- 六个 Demo 使用同一个工单、公共 API 和政策语义，分别展示 Understand、Act、Feedback/Prove、Control、Continue、Ground。
- 每次运行使用干净且隔离的工作区，并展示模型调用、工具活动、文件变化和最终验证结果。
- 同一 Demo 的两种模式只在目标 harness 能力上产生有意差异。
- 以少量直接的 Python 文件实现流程，允许 Demo 间重复，便于现场逐行解释。
- 保证 API 凭据不进入仓库、提示词或终端输出，并把模型的文件和命令权限限制在合成夹具内。

**Non-Goals:**

- 不进行统计有效的模型基准测试，也不宣称 harness 改变模型本身的智能水平。
- 不支持多个模型供应商适配器或同时维护多套 API 协议。
- 不构建通用 Agent SDK、插件机制、动态工具注册、数据库或持久化运行平台。
- 不接入真实业务代码、生产数据、公司系统或 MCP 服务。
- 不要求真实 LLM 在单次运行中产生完全可重复的回答。
- 不在本变更中优化成本、并发或大规模评测吞吐。

## Decisions

### 1. 使用一个共享运费夹具贯穿六个 Demo

夹具计划如下：

```text
fixtures/shipping/
├── AGENTS.md
├── DEMO_TICKET.md
├── src/
│   └── shipping.py
├── tests/
│   └── test_shipping.py
├── docs/
│   ├── integration-notes.md
│   └── cached-shipping-policy.md
└── provider/
    └── current-shipping-policy.json
```

`AGENTS.md` 声明只允许修改 `src/shipping.py` 和准确的验证命令；集成说明声明金额单位和公共 API 约束；缓存政策提供一份明确标注日期的旧版本；provider JSON 提供当前政策、版本和生效日期。

每个 Demo 选择性地向模型公开同一夹具中的信息。测试和政策数据始终用于最终评价，但只有当前 Demo 的 harness 流程可以把相应信息反馈给模型。

选择该方案而不是为每个 Demo 创建不同任务，是为了降低观众的认知负担，并让差异集中在 harness 组件上。代价是连续演示时观众会逐渐知道正确答案，因此现场只选择两到三个 Demo，或改变合成政策数值后重新演练。

### 2. 基线与 Harness 模式共用统一命令入口

CLI 使用标准库 `argparse`：

```bash
cd backend
uv run harness-demo 1
uv run harness-demo 1 --harness
uv run harness-demo list
```

数字代表独立实验，而不是累积级别。`--harness` 只启用该编号要展示的能力；基线仍可拥有准备工作区、调用 LLM 和最终评价所需的最小程序能力。

命令启动时打印 Demo 名称、模型名称、PLAIN/HARNESS 模式和本次唯一实验变量。无效编号在调用 LLM 前失败，并列出可用 Demo。

选择单入口而不是六个独立控制台命令，是为了让成对操作一致；分派之后的流程仍分别写在 `demo_*.py` 中，不建立通用 runner。

### 3. 使用官方 OpenAI SDK 直接管理调用循环

`backend/.env` 包含：

```dotenv
OPENAI_API_KEY=...
OPENAI_BASE_URL=...
OPENAI_MODEL=...
OPENAI_TIMEOUT_SECONDS=120
DEMO_MAX_TURNS=4
```

`llm.py` 负责加载并验证这些配置、创建 `OpenAI` 客户端，以及提供最小的文本调用辅助方法。演示路径不提供脚本适配器或无 API 降级。

首选 Responses API，因为应用需要直接观察并处理函数工具调用。应用自己管理工具执行、结果回传和停止条件，不采用 Agents SDK，以便现场展示 harness 实际做了什么。

选择一个很薄的共享 `llm.py`，而不是 provider adapter 接口，是因为首版只有一个 SDK 路径；额外抽象不会改善演示。

### 4. 每次运行从不可变夹具复制独立工作区

工作区位于 `backend/.demo-workspace/`，按 Demo 和模式分开：

```text
backend/.demo-workspace/
├── demo-1-plain/
├── demo-1-harness/
├── demo-2-plain/
└── demo-2-harness/
```

命令开始时只重建由程序根据固定 Demo 编号计算出的目录，不接受用户提供的删除目标。两种模式均从 `fixtures/shipping` 复制，避免上一次运行或另一种模式影响结果。

工作区准备函数可以作为一个短小的共享函数放在 CLI 模块中。除非实现变得难以阅读，否则不新增 workspace 服务层。

### 5. 六个 Demo 分别隔离一个 harness 能力

| Demo | 基线模式 | Harness 模式 | 主要证据 |
| --- | --- | --- | --- |
| 1 Understand | 只提供工单 | 增加源码、测试、`AGENTS.md` 和集成说明 | 正确文件、政策规则、API 约束、验证命令 |
| 2 Act | LLM 只返回建议或代码文本 | 提供受限的读文件、写文件和测试工具循环 | 实际 diff、工具记录、测试结果 |
| 3 Feedback / Prove | 写入一次生成结果，最后评价但不回传测试 | 测试失败后将摘要反馈给 LLM，允许继续修复 | 各轮测试结果、最终通过状态 |
| 4 Control | 在合成工作区内提供较宽的最小写入范围，不设人工审批 | 限定 `src/shipping.py`、限定命令、首次写入前审批 | 审批事件、越界拒绝、作用域检查 |
| 5 Continue | 第二个独立调用只获得原始任务和当前文件 | 第二个调用额外读取会话 A 的结构化进度记录 | 重复工作情况、下一步执行、最终测试 |
| 6 Ground | 只能依据缓存政策或模型已有知识 | 提供 `get_current_shipping_policy` 本地只读工具 | 工具调用、政策版本/日期引用、契约测试 |

Demo 1 只分析不修改文件，避免把上下文与行动混在一起。Demo 2 的基线输出不能被描述为已经完成修改。Demo 3 的两种模式使用相同初始生成输入，最终评价测试相同，区别仅在测试结果是否会在结束前反馈给模型。

Demo 4 的基线仍受演示程序的外层安全边界约束，不向 LLM 提供操作宿主机的任意 shell。该 Demo 证明的是系统约束和可审计性，不要求基线模型一定尝试越界。

Demo 5 在一次命令中创建两个不共享消息历史的 LLM 阶段。会话 A 负责调查并停止；Harness 模式把其结论写成包含已完成事项、关键发现、剩余工作和验证命令的进度记录，会话 B 显式读取该文件。

Demo 6 的工具读取本地 provider JSON，不访问其他外部服务。当前政策建议固定为版本 `2026-09`、生效日期 `2026-09-01`，从而让来源引用可以被确定性检查。

### 6. 工具接口保持最少且显式

Demo 2 至 Demo 4 只实现所需的三个工具概念：

- `read_file(path)`：只读取当前工作区内的文本文件；
- `write_file(path, content)`：按当前 Demo 的规则检查路径后写入；
- `run_tests()`：固定执行夹具声明的测试命令。

Demo 6 额外实现 `get_current_shipping_policy()`。工具定义和执行分支直接保留在使用它们的 Demo 文件中，即使因此产生少量重复。子进程使用参数数组、`shell=False`、固定 `cwd`、最小环境、超时和输出截断。

不提供 `run_command(command: str)`，因为它会让安全边界和现场解释都变复杂。

### 7. 最终评价独立于模型自述

每个 Demo 在结束时打印简短结果卡。确定性证据包括：

- 工作区中的实际文件列表和 diff；
- `pytest` 退出码；
- `git diff --check` 或等价的文本检查；
- 修改路径是否符合规则；
- 是否执行审批和政策工具；
- 报告中是否包含预期政策版本与日期。

Demo 1 的分析质量包含少量文本检查，例如是否出现目标文件、阈值、国际订单和验证命令。这些检查只用于现场提示，不把自然语言关键词命中率包装成严谨 benchmark。

终端输出采用固定标签，例如 `[LLM]`、`[TOOL]`、`[WRITE]`、`[TEST]`、`[FEEDBACK]` 和 `[RESULT]`，并限制模型与测试输出长度。首版不持久化通用 JSON 证据包。

### 8. 代码结构优先展示性

当前后端结构为：

```text
backend/src/harness_demo/
├── __init__.py
├── __main__.py
├── llm.py
├── common.py
├── demo_1_context.py
├── demo_2_tools.py
└── demo_3_feedback.py
```

`__main__.py` 解析参数、准备工作区并分派；`llm.py` 只处理配置与基础客户端；每个 Demo 文件直接表达自己的 PLAIN/HARNESS 分支。公共函数和 Demo 入口使用类型标注，但不增加抽象基类、依赖注入容器或通用状态机。

该选择接受少量重复，换取观众可以从一个文件看到完整实验流程。若后续多个 Demo 的工具协议确实完全相同，再做小范围提取，而不是预先设计框架。

### 9. 只测试确定性部分

自动化测试覆盖 CLI 解析、环境变量缺失、工作区重建、路径逃逸拒绝、命令白名单、评价函数和工具结果处理。测试可以注入一个很小的假客户端，但生产 CLI 没有选择假客户端的参数。

真实 LLM 行为通过演练验证，不断言具体措辞或单次成功率。正式演示前需要分别运行每一对命令，确认任务既不会简单到两边总是成功，也不会难到 Harness 模式在最大轮数内无法收敛。

## Risks / Trade-offs

- **[真实 LLM 输出有波动，基线偶尔也可能直接成功]** → 评价重点放在上下文、工具记录和客观证据，不只依赖成功/失败；正式分享前多次演练并准备录屏。
- **[同一个任务连续演示后，观众已知道答案]** → 现场只选两到三个代表性 Demo，或在演练时替换合成政策数值，但每个成对实验内部保持完全一致。
- **[Demo 3 第一次生成可能直接通过，反馈差异不明显]** → 保留“无需重试”作为合法结果；通过不直接暴露测试和一个不明显的国际订单规则提高触发反馈的概率，但不故意诱导错误答案。
- **[Demo 4 中模型可能自觉遵守范围，没有发生越界]** → 演示仍展示强制允许列表和审批事件，强调“模型愿意遵守”与“系统确保不能越界”的差别。
- **[简单任务让 Demo 5 的跨会话显得人为]** → 明确把会话切断作为教学条件，并限制会话 B 的轮数；不为证明连续性而扩大业务代码。
- **[兼容服务不支持 Responses API 或函数工具格式]** → 实现前用目标 `OPENAI_BASE_URL` 和 `OPENAI_MODEL` 做最小调用验证；若不支持，统一改用 Chat Completions，不维护双路径。
- **[模型工具调用可能请求意外参数或路径]** → 所有参数都按显式 schema 验证，路径解析后必须位于当前工作区，未知工具和无效参数作为错误结果返回模型。
- **[API Key 或服务信息被日志泄露]** → 不打印客户端配置、请求头和原始异常对象；只输出模型名称和经过截断、脱敏的错误摘要。
- **[为了公平而增加过多实验控制代码]** → 只固定模型、任务、初始夹具和评价命令；接受 harness 模式增加上下文与调用轮数，因为它们正是被展示的能力。

## Migration Plan

本变更不涉及数据迁移，已实现的 CLI 继续位于 `backend/`。当前进度与后续落地顺序如下：

1. 已完成依赖、控制台入口、`.env.example` 和忽略规则。
2. 已完成共享运费夹具和确定性测试。
3. 已完成 Demo 1、Demo 2 和 Demo 3 的实现及单元测试。
4. 待使用现场 LLM 配置完整演练三组成对命令。
5. 根据演示需要实现 Demo 4 至 Demo 6。

若后续实验实现方向不合适，可以单独回退相应 Demo；`backend/.demo-workspace` 始终是可丢弃内容，不承载源数据。
