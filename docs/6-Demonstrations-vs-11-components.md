• 结论：保留并完成这 6 个对照实验；不要把它们重构为与 PPT 的 11 个组件一一对应的 11 个 Demo。

  你看到的“不对应”并不是设计错误。PPT 的 11 项是 Harness 的实现/架构组件；6 个 Demo 是面向观众的可观察工程结果。同一个 Demo 必然会用到多个组件：例如“受限工具行动”同时涉及工具系统、输出解析、编排循环、安全边界与测试验证。强行拆成 11 个实
  验，反而会：

  - 让每个实验太小，难以形成“LLM 直接调用 vs Harness”可见差异；
  - 破坏“每次只解释一个主要变量”的现场讲解节奏；
  - 增加 LLM 波动、准备时间和演示失败点；
  - 让观众陷入组件术语，忽略最终的文件变更、审批、恢复和验证证据。

  而且 PPT 本身的 Demo 部分已经采用这套六实验框架：Context、Tools、Feedback、Control、Continue、Ground。它并没有主张把 11 个核心组件各做一个演示。见 /home/ubuntu/project/doc/Harness/Harness_full_redesign-20260912.pptx。

  建议把两者明确分成这个关系：

   面向观众的 Demo               主展示价值                          主要覆盖的 PPT 组件
  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   1. Understand / 项目上下文    给模型正确且相关的信息              上下文管理、提示词构建
  ────────────────────────────  ──────────────────────────────────  ──────────────────────────────────────────────────
   2. Act / 受限工具行动         从“建议”变成可控的真实操作          工具系统、输出解析、编排循环、安全防护、质量验证
  ────────────────────────────  ──────────────────────────────────  ──────────────────────────────────────────────────
   3. Prove / 测试反馈循环       用外部失败证据驱动有限修复          质量验证、异常处理、编排循环、状态记录
  ────────────────────────────  ──────────────────────────────────  ──────────────────────────────────────────────────

  ────────────────────────────  ──────────────────────────────────  ──────────────────────────────────────────────────

  因此，我建议的是“保留六个，但重新标注和补足证据”，不是“保留原样”：

  1. 在 Web UI 和讲解稿里为每个 Demo 显示“主组件 + 支撑组件”，避免观众误解为六项就是 Harness 的全部。
  2. 每次运行前用一句固定话术说明：
     “本次主要改变的是 X；其他运行保护仍是实验基础设施，不作为本次比较结论。”

  3. 把目前隐性的组件变得可见：
      - Demo 2 显示“结构化 tool call → 参数校验 → 受控执行”的链路，补足“输出解析”；
      - Demo 1 显示上下文来源与优先级摘要，补足“提示词构建”；
      - Demo 3 将测试失败归为“模型可修复异常”，显示最大轮数和停止原因，补足“异常处理/编排循环”；
      - Demo 5 展示可读的 handoff/checkpoint，而不只展示第二次模型回答。

  4. 不必为“子 Agent 编排”单独增加一个常规现场 Demo。它是唯一没有被六实验直接覆盖的核心组件；更适合先做成架构追踪视图或录制的进阶案例。只有当培训目标明确要求观众掌握并行分工、隔离与汇总时，才值得增加第 7 个可选 Demo。
  5. 完成优先级应是 Demo 4 → Demo 5 → Demo 6。Demo 4 最能体现企业 Harness 的差异化价值；Demo 5 覆盖当前最明显的状态/记忆缺口；Demo 6 则把“模型知识”与“可追溯事实来源”区分开来。

  当前项目实际上已经很好地遵循了这个方向：前三个可运行能力是 understand、act、prove，后三个 control、continue、ground 仍标为 planned，见 backend/src/harness_demo/web/catalog.py:10 与 README.md:15。现有设计文档也已经把六个 Demo 定义为“各
  自隔离一个主要 Harness 能力”，而非组件一对一映射，见 openspec/changes/archive/2026-09-07-add-live-harness-comparison-demos/design.md:137。
