# Harness 对照演示——设计文档

## 状态

当前实现与后续设计。Python 演示已迁入 `backend/`，Demo 1 至 Demo 3 已实现；Demo 4 至 Demo 6 仍是候选设计。`frontend/` 已初始化，页面实现由对应 OpenSpec change 管理。

## 目的

通过实际调用 LLM，直观展示同一个模型在没有 harness 支持和增加某项 harness 能力后，完成工程任务的效果差异。

演示关注的不是“harness 让模型本身变聪明了”，而是：当模型获得更完整的上下文、可执行工具、运行反馈、边界控制、会话状态或外部依据后，它能否更可靠地完成原本无法完成或容易出错的任务。

每个 Demo 都采用成对运行：

```text
同一个模型 + 同一个任务 + 同一份初始夹具
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
     不带 --harness      带 --harness
      基线运行             增加一个核心能力
          │                   │
          └─────────┬─────────┘
                    ▼
            比较可观察的结果
```

## 核心原则

### 1. 每次运行都调用真实 LLM

- 不使用脚本适配器生成预设回答。
- 不提供“无 API 时自动使用假结果”的降级路径。
- 正常运行时，无论是否带 `--harness`，都至少调用一次 LLM。
- API 调用失败时明确报错并退出，不将失败伪装成模型结果。

### 2. 每个 Demo 是独立实验

- Demo 编号代表不同的 harness 能力，不代表逐级累积的 level。
- 每个 Demo 都有自己的任务、夹具、提示词、执行流程和评价标准。
- 不要求先运行前一个 Demo。
- 当前六个 Demo 统一使用运费规则升级任务，降低连续演示时的认知负担。
- 为了让单个 Demo 清晰易懂，允许不同脚本中存在少量重复代码。

### 3. `--harness` 只表示启用当前 Demo 的目标能力

“不带 harness”并不意味着程序内部完全没有任何辅助代码。程序仍需要完成 API 调用、准备夹具和展示结果等基本工作。

对于测试反馈、审批控制等实验，基线运行也可以具备完成对照所需的最小文件写入能力。两种模式的关键区别应只有当前 Demo 想展示的 harness 组件。

例如，测试反馈 Demo 中：

- 基线模式允许把 LLM 第一次生成的代码写入工作区，但不会把测试结果反馈给 LLM。
- Harness 模式使用相同的首次生成流程，并额外运行测试、把失败信息反馈给 LLM，再让它修复。

### 4. 以工程结果评价，不只比较回答文字

每个 Demo 都应定义简单且可观察的评价结果，例如：

- 是否识别出正确文件；
- 是否提到关键约束；
- 是否真正修改了工作区；
- 测试是否通过；
- 是否修改了禁止修改的文件；
- 新会话能否继续之前的任务；
- 是否引用了工具提供的当前信息。

LLM 的最终回答可以展示，但不能作为唯一成功依据。

### 5. 优先保证演示清晰，不追求工程化

- 不构建通用智能体框架。
- 不设计插件系统、动态工具发现或复杂适配器层。
- 不使用数据库。
- 不为所有 Demo 建立统一状态机。
- 不为消除几行重复代码而引入抽象。
- 仅复用 `.env` 加载、OpenAI 客户端创建等非常基础的代码。

## 命令行界面

以下命令均在 `backend/` 中执行。统一命令格式为：

```bash
# 基线模式
uv run harness-demo 1

# 为 Demo 1 启用对应的 harness 能力
uv run harness-demo 1 --harness
```

其他 Demo 使用相同形式：

```bash
uv run harness-demo 2
uv run harness-demo 2 --harness

uv run harness-demo 3
uv run harness-demo 3 --harness
```

命令约定：

- 第一个位置参数是 Demo 编号。
- 默认运行基线模式。
- `--harness` 启用该 Demo 要展示的 harness 能力。
- 无效编号返回非零退出码，并列出已实现的 Demo。
- 每次运行从对应夹具生成干净工作区，避免上一次运行影响结果。
- 命令开始时打印 Demo 名称、模型、运行模式和本次启用的能力。

可以增加一个只读辅助命令：

```bash
uv run harness-demo list
```

它只列出演示编号、主题和两种模式的差别，不调用 LLM。

## LLM 调用

### SDK 与 API

使用官方 OpenAI Python SDK，直接创建 `OpenAI` 客户端。首版使用 Responses API：

```python
from openai import OpenAI

client = OpenAI(
    api_key=settings.api_key,
    base_url=settings.base_url,
)

response = client.responses.create(
    model=settings.model,
    input=prompt,
)
```

不使用 OpenAI Agents SDK。演示程序需要直接展示并控制上下文拼装、工具调用、反馈循环和状态传递，因此这些行为应写在各 Demo 脚本中。

如果实际 `OPENAI_BASE_URL` 对应的服务不支持 Responses API，而只支持 Chat Completions API，则在实现前统一将最小调用封装改为 `client.chat.completions.create`。首版不同时维护两套 API 路径。

### 环境配置

真实配置保存在后端项目根目录 `backend/.env`：

```dotenv
OPENAI_API_KEY=your-api-key
OPENAI_BASE_URL=https://api.openai.com/v1
OPENAI_MODEL=your-model-name

OPENAI_TIMEOUT_SECONDS=120
DEMO_MAX_TURNS=4
```

规则：

- `OPENAI_API_KEY`、`OPENAI_BASE_URL` 和 `OPENAI_MODEL` 是必填项。
- `.env` 必须加入 `.gitignore`，不得提交。
- 后端提供 `backend/.env.example`，其中只放占位值。
- API Key 不打印到终端，不写入提示词、证据文件或异常详情。
- `OPENAI_BASE_URL` 只用于客户端初始化，不作为任务上下文发送给模型。
- 超时和最大工具循环次数必须有较小的固定上限，避免现场演示失控。

### 公平对照

同一个 Demo 的两种模式尽量保持以下条件一致：

- 使用同一个 `OPENAI_MODEL`；
- 使用同一个任务文本；
- 使用相同的初始夹具；
- 使用相同的输出要求；
- 使用相同或相近的最大调用轮数；
- 除目标 harness 能力外，不额外改变模型可获得的信息和权限。

Harness 模式必然会增加上下文、工具定义或反馈消息，这正是实验变量，不需要强行保持提示词字面完全一致。

真实 LLM 输出存在波动。演示展示的是具体运行中的可观察差异，不声称单次结果构成统计意义上的模型评测。如需提高现场稳定性，可以提前演练并保留一次成功录屏，但现场命令仍然调用真实 LLM。

## Demo 设计

整体设计包含六个相互独立的 Demo。差异最明显的 Demo 1、2、3 已完成，Demo 4 至 Demo 6 根据后续演示需求实现。

### Demo 1：上下文——Understand

目标：展示完整项目上下文如何改善分析质量。

任务使用一个小型 Python 缺陷。真正的修复要求藏在源码、测试和一份集成说明中，仅看工单无法可靠推断。

基线模式：

- 只把工单文本发给 LLM。
- 要求它分析原因并提出修改方案。
- 不提供源码、测试或项目说明。

Harness 模式：

- 程序读取与任务相关的源码、测试、`AGENTS.md` 和集成说明。
- 将这些内容组成带文件名边界的上下文包。
- 把相同工单与上下文包一起发给 LLM。

比较结果：

- 是否定位到正确源文件；
- 是否指出真实失败原因；
- 是否保留公共 API；
- 是否给出项目规定的验证命令。

此 Demo 只要求分析，不修改文件，以便把变量集中在“上下文”上。

### Demo 2：工具——Act

目标：展示“能够提出代码”与“能够实际完成工作区变更”的区别。

基线模式：

- 向 LLM 提供任务和必要代码。
- LLM 只能返回建议或代码文本。
- 程序展示回答，但不把它当作已经完成的仓库修改。

Harness 模式：

- 为 LLM 提供少量明确工具，例如读取文件、写入指定文件和运行固定测试命令。
- 程序执行模型请求的工具调用，并把工具结果返回给模型。
- 工具循环达到完成状态或最大轮数后停止。

比较结果：

- 工作区是否真的产生修改；
- 修改是否位于目标文件；
- 测试命令是否被实际执行；
- 最终工作区是否满足任务要求。

工具只面向合成工作区，不提供任意系统 shell。

### Demo 3：测试反馈——Prove / Feedback Loop

目标：展示测试结果反馈如何帮助 LLM 发现并修复第一次实现中的问题。

任务应故意包含一个容易遗漏的边界条件，使 LLM 的第一次修改有机会不完整，但测试能够明确暴露问题。

两种模式共同具备：

- 相同的源码和测试；
- 相同的任务描述；
- 把 LLM 第一次生成的完整目标文件写入独立工作区；
- 在 LLM 结束后运行同一条最终评价命令。

基线模式：

- 只调用 LLM 一轮生成修改。
- 不把测试执行结果反馈给 LLM。
- 最终测试仅用于演示程序评价结果。

Harness 模式：

- 写入第一次修改后立即运行测试。
- 如果失败，将精简后的测试输出反馈给 LLM。
- 允许 LLM 根据反馈再次修改，最多执行固定的小轮数。
- 每轮都打印“修改 → 测试 → 反馈”的过程。

比较结果：

- 首次修改是否通过；
- Harness 模式使用了几轮；
- 最终测试是否通过；
- LLM 是否根据失败信息修正了对应边界条件。

### Demo 4：边界与审批——Control

目标：展示 harness 对操作范围和关键动作的控制，而不是单纯追求更多工具。

两种模式都在一次性的合成工作区内运行，外层程序始终保留最低安全边界。

基线模式：

- LLM 可以直接请求修改夹具内的多个文件。
- 不提供项目级“只允许修改哪些文件”的明确执行约束。
- 不设置人工审批点。

Harness 模式：

- 只允许修改声明的实现文件。
- 只允许运行固定命令。
- 首次写入前在终端展示计划，并等待人工确认。
- 越界工具请求被拒绝，并把拒绝原因返回给 LLM。

比较结果：

- 是否修改了禁止修改的测试或配置；
- 是否在审批前执行写操作；
- 被拒绝后能否调整方案；
- 最终结果是否同时满足功能和作用域要求。

此 Demo 主要展示可靠性、权限和可审计性，不预设 Harness 模式一定生成“更聪明”的代码。

### Demo 5：跨会话状态——Continue

目标：展示新的 LLM 会话如何依靠外部状态继续未完成工作。

一次命令内明确创建两个相互独立的 LLM 调用阶段，不依赖上一阶段的内存对话。

会话 A：

- 检查任务；
- 完成部分工作或形成计划；
- 随后结束。

基线模式的会话 B：

- 只获得原始任务和当前工作区；
- 不获得会话 A 的进度摘要。

Harness 模式的会话 B：

- 额外读取会话 A 生成的结构化进度记录；
- 进度记录包含已完成事项、未完成事项、关键发现和下一步验证命令。

比较结果：

- 会话 B 是否重复已经完成的工作；
- 是否理解当前工作区状态；
- 是否能接着正确的下一步继续；
- 最终任务是否完成。

### Demo 6：外部依据——Ground

目标：展示本地只读工具如何为 LLM 提供当前且有来源的信息。

任务涉及一个模型仅凭已有知识无法确定的“当前提供方策略”。权威答案保存在本地合成数据中。

基线模式：

- 只提供任务文本。
- LLM 只能依赖提示词和自身已有知识回答或实现。

Harness 模式：

- 向 LLM 提供本地只读函数工具 `get_provider_retry_policy`。
- 工具返回策略版本、生效日期和明确的重试规则。
- LLM 使用工具结果完成代码或报告。

比较结果：

- 是否调用工具；
- 是否采用正确的当前规则；
- 是否引用策略版本和生效日期；
- 最终实现是否满足夹具中的契约测试。

该工具是本地函数，不使用 MCP，不连接真实公司系统。除调用 LLM 所需网络外，不访问其他外部服务。

## 夹具与工作区

当前已实现的 Demo 1 至 Demo 3 共用一个最小运费夹具：

```text
backend/fixtures/shipping/
├── AGENTS.md
├── DEMO_TICKET.md
├── src/shipping.py
├── tests/test_shipping.py
└── docs/
    ├── integration-notes.md
    └── shipping-policy.md
```

夹具要求：

- 只包含完成该 Demo 所需的最少文件。
- 使用合成业务、虚构域名和非敏感数据。
- 尽量使用几十行代码可以解释清楚的问题。
- 基线和 Harness 模式必须从相同初始内容开始。
- 每次运行前复制到独立工作区，例如：

```text
backend/.demo-workspace/
├── demo-1-plain/
└── demo-1-harness/
```

工作区加入 `.gitignore`。程序只重建已知的 Demo 工作区路径，不接受任意删除路径。

## 终端输出

输出本身是演示的一部分，应简短、分阶段且便于观众理解。

建议格式：

```text
Demo 3: 测试反馈
模式: HARNESS
模型: <model>
启用能力: 测试执行 + 失败反馈 + 再次修复

[LLM] 生成第一次修改
[WRITE] src/shipping.py
[TEST] 1 failed, 4 passed
[FEEDBACK] 将失败摘要返回 LLM
[LLM] 生成第二次修改
[TEST] 5 passed

结果: PASS
```

需要展示：

- 本次实验变量；
- LLM 调用轮次；
- 工具请求和结果摘要；
- 文件变更列表；
- 测试或评价结果；
- 最终通过/失败。

不要展示：

- API Key；
- 包含凭据的请求头；
- 与当前 Demo 无关的大段调试日志；
- 无长度限制的模型输出或测试输出。

首版不需要把每次运行结果持久化成复杂的 JSON 证据包。终端输出和最终工作区足以支持演示。

职责约定：

- 每个 `demo_*.py` 直接写清自己的基线流程和 Harness 流程。
- 某个工具只被一个 Demo 使用时，直接写在该 Demo 文件中。
- 只有确定被多个 Demo 使用且抽取后更清晰的代码才进入公共模块。

不创建 `runner.py`、`levels.py`、adapter 层、插件注册表或通用工作流引擎。

## 依赖

首版只引入必要依赖：

```toml
dependencies = [
    "openai",
    "python-dotenv",
]
```

测试可以使用项目已有或开发依赖中的 `pytest`。不为命令行引入 Typer、Click 等额外框架，使用标准库 `argparse` 即可。

## 测试策略

这是现场演示项目，测试重点是确定性代码，不尝试断言真实 LLM 每次必须返回相同内容。

最少覆盖：

1. 缺少必要环境变量时给出明确错误。
2. CLI 能正确解析 Demo 编号和 `--harness`。
3. 每次运行能从同一夹具创建干净工作区。
4. 写文件工具不能逃出当前 Demo 工作区。
5. 固定命令工具拒绝未允许的命令。
6. 各 Demo 的最终评价函数能正确判断通过和失败。

LLM 集成通过人工运行命令验证。实现期间可以为测试注入一个返回固定内容的轻量假客户端，但它只能用于单元测试，不能成为演示命令的运行模式。

## 安全边界

尽管项目追求最简，仍保留以下边界：

- `backend/.env` 和 `backend/.demo-workspace/` 不进入版本控制。
- 所有任务数据均为合成数据。
- 所有文件修改限定在当前 Demo 工作区。
- 不向模型或终端输出泄露凭据。
- 子进程使用固定当前目录、`shell=False`、超时和输出长度限制。
- 不为 LLM 提供任意系统命令执行能力。
- 现场使用的 API 账户应设置合理的调用额度。

## 演示建议

现场不必运行所有 Demo。优先选择两个或三个差异最直观的实验，每个实验按以下顺序展示：

```bash
cd backend
uv run harness-demo <编号>
uv run harness-demo <编号> --harness
```

先让观众看到基线结果，再启用对应能力，并在第二次运行前明确说明“这次只增加了什么”。结束时展示测试、diff、工具记录或进度状态等客观结果。

真实模型有随机性，正式分享前应多次演练任务难度和提示词。任务不能简单到两种模式总是成功，也不能难到 Harness 模式在有限轮数内仍无法完成。

## 非目标
