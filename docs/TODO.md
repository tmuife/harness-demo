# Harness 组件与 Demo 对应

现有 6 个 Demo 展示用户可感知的 Harness 能力；11 个核心组件是实现这些能力的系统结构。因此不应强行一一对应，一个 Demo 可以使用多个组件。

| Demo | 主要组件 | 辅助组件 | 说明 |
| --- | --- | --- | --- |
| 1 上下文（Understand） | 上下文管理、提示词构建 | — | 当前展示的是补充上下文，尚未覆盖上下文压缩与 Token 控制。 |
| 2 工具行动（Act） | 工具系统 | 编排循环、输出解析、护栏与安全 | 解析工具调用、执行并将结果回传模型。 |
| 3 测试反馈（Prove） | 验证循环 | 编排循环、错误处理 | 展示“修改 → 测试 → 反馈 → 修复”的闭环。 |
| 4 边界审批（Control） | 护栏与安全 | 工具系统、编排循环 | 展示路径和命令限制，以及人工审批。 |
| 5 跨会话状态（Continue） | 记忆系统 | 状态管理 | 结构化交接记录帮助新会话继续任务。 |
| 6 外部依据（Ground） | 工具系统 | 提示词构建 | 工具用于取得可信的当前策略。 |

## 关键结论

- 建议在 11 个组件之外明确增加 **外部依据（Grounding / Retrieval）**：Demo 6 的核心不是“有工具”，而是使用可追溯的权威信息。
- 编排循环、输出解析、提示词构建和错误处理是跨 Demo 的基础能力，不必各自成为一个 Demo。
- Demo 5 当前更偏“记忆”：它保存并提供已知信息。若展示“状态管理”，应增加检查点、恢复或回滚等可观察行为。

```text
用户可见能力：Understand · Act · Prove · Control · Continue · Ground
底层支撑组件：提示词构建、编排循环、输出解析、错误处理、
                上下文管理、工具系统、验证循环、护栏与安全、
                记忆系统、状态管理、子智能体编排
```

## 候选后续 Demo

- Demo 7｜韧性与恢复：展示网络超时、限流或工具失败后的分类处理、重试和恢复。
- Demo 8｜子智能体协作：展示调查、实现、验证等独立角色的分工与结果汇总。
